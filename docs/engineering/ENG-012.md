ENG-012 — BACKEND API INTEGRATION

You are implementing ENG-012 in the ClipForge monorepo.

IMPORTANT:
ENG-012 is strictly a Backend API Integration scope.

Do NOT modify unrelated application UI, pages, layout, navigation, shared types, service-layer contracts, upload/queue/download behavior, authentication, or business logic unless explicitly required to connect the existing service layer to the existing backend API.

ENG-010 (Shared Types) and ENG-011 (Service Layer) are already completed, committed, and pushed. Treat them as the current baseline.

OBJECTIVE

Connect the existing frontend service layer from ENG-011 to the existing backend API.

The goal is to establish the real frontend → API → backend integration boundary without redesigning the application.

SCOPE

Inspect the existing repository and reference repository before making changes.

1. BACKEND API CONTRACT

Inspect the existing backend routes/controllers/API implementation.

Identify:

- Existing API endpoints
- HTTP methods
- Request parameters/body
- Response shapes
- Error responses
- Upload-related endpoints
- Job creation/status endpoints
- Queue/job endpoints
- Download-related endpoints

Do NOT invent new endpoints.

Use the existing backend contract wherever possible.

2. API CLIENT INTEGRATION

Integrate:

frontend/src/services/api.client.ts

with the actual backend API.

Use the repository's existing API configuration/environment conventions.

Do not hardcode production URLs.

If the project already defines VITE_API_BASE_URL or an equivalent configuration, reuse it.

Do not introduce a second API-client architecture.

3. SERVICE INTEGRATION

Connect the existing ENG-011 services to the API client:

- frontend/src/services/job.service.ts
- frontend/src/services/upload.service.ts
- frontend/src/services/queue.service.ts
- frontend/src/services/download.service.ts
- frontend/src/services/index.ts

Preserve their existing public interfaces wherever possible.

Do not redesign the service layer.

The purpose of ENG-012 is to replace placeholder/mock/incomplete transport behavior with the actual backend API communication where the backend already supports it.

4. ERROR HANDLING

Ensure API failures are represented consistently through the existing service/API-client architecture.

Handle:

- HTTP errors
- Network failures
- Invalid/unexpected responses

Do not introduce a large new error-handling framework.

Keep the implementation minimal and appropriate for the MVP.

5. REQUEST/RESPONSE CONTRACTS

Use the canonical shared types from ENG-010 wherever they apply.

Do not duplicate domain types unnecessarily.

If an API response differs from the canonical domain type, create only the smallest necessary mapping/adapter at the service boundary.

Do not modify ENG-010 shared types unless absolutely necessary.

If modification is genuinely required, STOP and report it instead of silently changing scope.

6. AUTHENTICATION

Do NOT implement a new authentication system.

Do NOT change existing authentication behavior.

If the existing backend requires authentication and the repository already contains an authentication mechanism, integrate with that mechanism only.

If authentication is not yet available, document the limitation and leave it for the appropriate later scope.

7. BACKEND

Inspect backend code to understand the existing API.

Do NOT create new backend endpoints unless the existing architecture makes an already-defined required contract impossible to consume.

Do NOT redesign backend architecture.

Do NOT modify database schemas.

Do NOT modify FFmpeg/video-processing logic.

Do NOT modify upload processing, queue workers, or job execution internals.

ENG-012 is an integration boundary, not a backend feature-development ticket.

8. FRONTEND PAGES

Do NOT modify:

- frontend/src/pages/HomePage.tsx
- frontend/src/pages/JobStatusPage.tsx

unless a minimal import/type adjustment is technically unavoidable for compilation.

Do not change their UI or application behavior as part of this ticket.

9. SCOPE BOUNDARIES

The following must remain untouched unless strictly required for API integration:

- frontend/src/components/
- frontend/src/layouts/
- frontend/src/hooks/
- frontend/src/lib/
- frontend/src/constants/
- packages/shared/
- database/schema
- authentication implementation
- FFmpeg/video processing
- queue workers
- application UI

Do not perform unrelated cleanup or refactoring.

10. ENVIRONMENT CONFIGURATION

Inspect the existing environment configuration.

If the repository already has an API base URL convention, use it.

If an environment variable is required but missing, add only the minimum necessary example/documentation configuration.

Never commit secrets, API keys, tokens, passwords, or private credentials.

11. VERIFICATION

After implementation, run the repository's existing verification suite.

At minimum run:

npm run build:shared
npm run type-check
npm run lint
npm run build

If additional existing API/service tests are available, run the relevant tests.

Do not weaken, bypass, or modify tests merely to make them pass.

12. SCOPE AUDIT

Before stopping, run:

git status --short

git diff --name-only

git diff --stat

Audit every changed file against ENG-012.

Explicitly confirm:

- Which files belong to ENG-012
- Which files were intentionally untouched
- Whether any existing API endpoints were reused
- Whether any endpoints had to remain unintegrated because the backend does not currently expose them
- Whether any files outside ENG-012 were changed

If an unrelated file was modified accidentally, revert ONLY that unrelated modification before completing the ticket.

13. DOCUMENTATION

Create:

docs/engineering/ENG-012.md
docs/engineering/ENG-012_Change_Log.md
docs/engineering/ENG-012_Implementation_Report.md

The documentation must accurately describe what was actually implemented.

Do not claim endpoints or functionality were implemented if they do not exist.

14. STOP CONDITION

When implementation and verification are complete:

STOP.

Do NOT commit.

Do NOT push.

Do NOT stage files.

Report:

1. Files created
2. Files modified
3. Files untouched
4. Backend endpoints discovered and integrated
5. Endpoints that could not be integrated and why
6. Environment/API configuration used
7. Verification results
8. Final git status
9. Final git diff --name-only
10. Scope compliance assessment

The working tree must remain available for CTO review.

IMPORTANT:
Do not make assumptions about missing backend functionality.
Do not invent API endpoints.
Do not silently expand ENG-012.
Do not commit or push.
