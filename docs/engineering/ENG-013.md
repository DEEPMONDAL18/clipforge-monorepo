ENG-013 — END-TO-END TESTING

You are implementing ENG-013 in the ClipForge monorepo.

IMPORTANT:
ENG-013 is strictly an End-to-End Testing and integration verification scope.

ENG-007 through ENG-012 have been completed and committed/pushed. Treat the current main branch as the baseline.

Do NOT redesign or refactor the application.
Do NOT add product features.
Do NOT modify backend business logic merely to make tests pass.
Do NOT modify the UI unless a minimal testability adjustment is absolutely required.
Do NOT invent APIs, routes, or application behavior.

OBJECTIVE

Verify that the ClipForge application works correctly across the complete user-to-backend flow using the existing implementation from ENG-007 through ENG-012.

The purpose of ENG-013 is to discover integration failures before production release.

FIRST: REPOSITORY AUDIT

Before writing or modifying tests:

1. Inspect the existing frontend architecture.
2. Inspect the existing backend routes and services.
3. Inspect the ENG-010 shared types.
4. Inspect the ENG-011 service layer.
5. Inspect the ENG-012 API integration.
6. Inspect package.json files and determine the existing testing framework/tooling.
7. Inspect any existing tests.

Do NOT install a new testing framework if an appropriate testing framework already exists.

If no E2E framework exists, determine the smallest appropriate approach based on the repository's existing dependencies and architecture.

TEST SCOPE

Create a practical MVP end-to-end verification suite covering the critical application flows.

At minimum verify:

1. APPLICATION STARTUP

- Frontend starts successfully.
- Backend starts successfully using the existing development configuration.
- No fatal console/runtime errors occur during startup.

2. APPLICATION SHELL
   Verify that the application can load its main layout/navigation structure.

Check:

- Navbar
- Main content area
- Footer
- Theme toggle where applicable

Do not redesign these components.

3. LANDING / HOME FLOW
   Verify the existing HomePage loads successfully.

Verify that the primary application controls required for the clipping workflow are present and usable.

Do not invent UI behavior. Test only behavior that actually exists.

4. UPLOAD FLOW
   Verify the existing upload flow using a safe test fixture.

Test the actual frontend service → API → backend path where practical.

Verify:

- Upload initialization
- Upload request/chunk handling where applicable
- Upload status handling
- Error handling
- Abort/cancel behavior where supported

Do not upload large real-world media files unnecessarily.

Use a small deterministic test fixture.

5. JOB FLOW
   Verify the job-related API/service integration.

Where the current backend supports it, verify:

- Job retrieval
- Job progress
- Job clips
- Job cancellation
- Job deletion

Use actual existing backend contracts.

Do not create fake endpoints simply to satisfy the test.

6. QUEUE FLOW
   Verify the existing queue service integration.

Verify that queue statistics/snapshot requests correctly communicate with the backend.

7. DOWNLOAD FLOW
   Verify the existing download service integration.

Verify that archive/clip URL resolution uses the existing backend API contract.

Do not download large files unnecessarily.

8. ERROR HANDLING

Test at least one realistic failure condition.

Examples:

- invalid job ID
- unavailable resource
- invalid upload request
- backend/API failure

Use whichever scenario is supported naturally by the existing application.

Verify that the frontend does not crash and that the error is handled through the existing architecture.

9. API CONTRACT VERIFICATION

Verify that the frontend services from ENG-011/ENG-012 communicate with the existing backend routes.

Relevant existing routes include:

/api/v1/upload/*
/api/v1/jobs/*
/api/v1/queue/*
/api/v1/download/*

Do NOT invent additional routes.

10. RESPONSIVENESS / BASIC UI SANITY

Perform basic verification that the primary application flow renders without layout-breaking runtime errors at normal desktop dimensions.

Do not turn ENG-013 into a visual redesign or comprehensive browser compatibility project.

TEST DATA

Create only minimal deterministic test fixtures if required.

Do not include:

- real credentials
- API keys
- production tokens
- private user data
- large media files

Do not commit secrets.

BACKEND / DATABASE SAFETY

Do not run destructive operations against production resources.

If the repository has a development/test database or mock environment, use that.

If a required E2E scenario cannot safely be executed because the repository lacks a test environment or deterministic fixture, document the limitation instead of modifying production logic.

TEST IMPLEMENTATION

Keep tests:

- deterministic
- repeatable
- isolated
- understandable
- appropriate for an MVP

Do not create an unnecessarily large test suite.

Prefer testing the critical user journey and integration boundaries rather than achieving an arbitrary coverage percentage.

REGRESSION PROTECTION

Existing tests must continue to pass.

Do not weaken or delete existing tests.

Do not modify application code simply to hide test failures.

If an actual application defect is discovered:

1. Document the failure.
2. Identify the responsible file/component/service.
3. Explain whether it belongs to ENG-013 or a later corrective scope.
4. STOP before making unrelated production fixes.

VERIFICATION

Run the repository's existing verification commands.

At minimum run the appropriate existing commands for:

- shared package build
- TypeScript type checking
- linting
- production build
- existing unit/integration tests
- ENG-013 E2E tests

Use the actual scripts defined in package.json.

Do not assume script names if they differ from the repository.

SCOPE BOUNDARY

ENG-013 may create or modify TEST files and ENG-013 documentation.

Do not modify unrelated production files unless a genuine testability defect makes it unavoidable.

Do NOT modify:

- database schemas
- FFmpeg implementation
- authentication architecture
- API contracts
- shared domain types
- service architecture
- application layout
- unrelated application pages
- unrelated components
- production configuration

unless a discovered defect makes such a change strictly necessary.

If such a change appears necessary, STOP and report it for CTO review.

DOCUMENTATION

Create:

docs/engineering/ENG-013.md
docs/engineering/ENG-013_Change_Log.md
docs/engineering/ENG-013_Implementation_Report.md

The documentation must accurately record:

- testing strategy
- tests created
- flows tested
- commands executed
- test results
- failures discovered
- known limitations
- files changed
- files intentionally untouched

Do not claim an E2E scenario passed if it could not actually be executed.

FINAL SCOPE AUDIT

Before stopping, run:

git status --short
git diff --name-only
git diff --stat

Audit every changed file.

Confirm:

1. Which files were created.
2. Which files were modified.
3. Which production files, if any, were modified and why.
4. Which files were intentionally untouched.
5. Which E2E flows passed.
6. Which flows failed.
7. Whether failures are application defects, environment limitations, or test issues.
8. Whether any scope boundary was crossed.

STOP CONDITION

After implementation and verification:

DO NOT commit.
DO NOT push.
DO NOT stage files.

Stop and provide a concise CTO review report containing:

1. E2E test framework used
2. Tests created
3. Critical flows tested
4. Test results
5. Existing verification results
6. Failures and their root causes
7. Known limitations
8. Changed files
9. Scope compliance assessment
10. Final git status

The working tree must remain uncommitted and available for CTO review.
