# ENG-009 — Application Pages Migration

## Engineering Ticket

ID: ENG-009

Title: Application Pages Migration

Priority: Critical

Sprint: 2C

Status: Planned

---

# OBJECTIVE

Migrate the application pages from the Lovable reference repository
(`clipforge-frontend`) into the production ClipForge monorepo
(`Clipping Software`).

ENG-009 builds the actual application screens on top of the shared UI
components established in ENG-007 and the layout/navigation shell
established in ENG-008.

This ticket covers APPLICATION PAGES ONLY.

No backend integration.

No service-layer migration.

No API integration.

No authentication implementation.

No upload/queue/business-logic redesign.

---

# REPOSITORIES

## Repository A — TARGET

`Clipping Software`

This is the production ClipForge monorepo.

ALL implementation work MUST occur here.

---

## Repository B — REFERENCE

`clipforge-frontend`

This is the original Lovable-generated frontend.

Treat this repository as STRICTLY READ ONLY.

DO NOT:

- modify files
- delete files
- move files
- rename files
- install packages
- commit changes

Use it only to inspect and migrate the required application-page
implementations.

# ROLE

Do not redesign the application.

Do not introduce new technologies.

Implement only the scope defined in ENG-009.

# IMPORTANT BUSINESS-LOGIC RULE

The Lovable pages may contain references to functionality that belongs
to later engineering tickets.

If a page contains dependencies on:

- API calls
- backend services
- upload processing
- queue processing
- FFmpeg
- authentication
- persistent job management
- production service logic
- business rules

DO NOT migrate or redesign those systems as part of ENG-009.

Instead:

1. Preserve the page structure where possible.
2. Use existing production interfaces if they already exist.
3. Do not invent replacement backend logic.
4. Do not create fake production APIs.
5. Document unresolved dependencies for the appropriate future ticket.

# MIGRATION RULES

1. Prefer the smallest change that achieves the objective.

2. Preserve existing production code where it already satisfies the
   requirement.

3. Preserve existing import aliases.

4. Preserve existing project structure.

5. Reuse existing utilities.

6. Do not add dependencies unless absolutely required.

7. If a dependency is required, document:
   - package name
   - reason
   - why an existing dependency cannot be used

8. Do not migrate Lovable-specific infrastructure that is not required
   by the application pages.

9. Do not copy unnecessary Lovable configuration files.

10. Do not copy Lovable-specific backend code.

11. Do not modify `clipforge-frontend`.
